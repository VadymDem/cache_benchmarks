# cache_benchmarks

Бенчмарк кеш-пам'яті, шаблонів доступу та перегонів даних, написаний на C11.
Одна програма без зовнішніх залежностей вимірює шість незалежних ефектів на
реальному залізі й пише результат у CSV.

Робота виконана в межах лабораторної роботи з дисципліни «Сучасні операційні
системи». Повний опис методики, таблиці вимірювань і висновки — у
`Звіт_ЛР.docx`.

## Що вимірюється

| Секція | Ключ | Що показує |
|---|---|---|
| Ієрархія пам'яті | `lat` | Затримка залежного доступу від 16 КБ до 128 МБ: L1 → L2 → L3 → DRAM |
| Крок доступу | `stride` | Ціна доступу при кроці 8 Б … 4 КБ, трафік кеш-ліній, оцінка розміру лінії |
| Множення матриць | `matmul` | `ijk` проти `ikj`, блочного 64×64 і варіанта з транспонуванням |
| False sharing | `share` | Вісім лічильників в одній кеш-лінії проти рознесених по лініях |
| Перегони даних | `race` | `volatile` проти `atomic`, `mutex` і padded-atomic |
| Обхід матриці | `rows` | Посумковий обхід рядками проти обходу стовпцями |

## Вимоги

- Windows (MinGW-w64 GCC) або Linux/macOS (GCC/Clang);
- компілятор з підтримкою C11 `<stdatomic.h>`;
- для збірки на Windows — `build.bat`, на POSIX — команда `gcc` вручну.

## Збірка

Windows:

```bat
build.bat
```

Вручну (будь-яка платформа):

```sh
gcc -O3 -march=native -Wall -Wextra -std=gnu11 -o cache_bench cache_bench.c
```

`-O3` важливий: частина ефектів (наприклад, викидання циклу суми) проявляється
саме на оптимізованому коді. `-march=native` вмикає векторизацію, яка теж
впливає на результати матричних тестів.

## Запуск

```bat
cache_bench.exe                        :: усі секції, results/lab3.csv
cache_bench.exe results\my.csv         :: свій шлях до CSV
cache_bench.exe results\my.csv share   :: лише одна секція
cache_bench.exe --selftest             :: самотестування, код виходу 0/1
```

Секції: `all`, `lat`, `stride`, `matmul`, `share`, `race`, `rows`.
Повний прогін на 8 ядрах займає приблизно 1–2 хвилини.

## Змінні середовища

| Змінна | За замовчуванням | Призначення |
|---|---|---|
| `LAB3_THREADS` | 8 | Кількість потоків у конкурентних тестах |
| `LAB3_MAX_MB` | 128 | Найбільший розмір набору в тесті затримки, МБ |
| `LAB3_LAT_ACCESSES` | 0 (авто) | Кількість випадкових доступів на точку; 0 — 4 млн для малих наборів і 2 млн для великих |
| `LAB3_STRIDE_MB` | 64 | Обсяг корисного навантаження в тесті кроку, МБ |
| `LAB3_MATMUL_N` | 1024 | Розмір матриці в тесті множення |
| `LAB3_MATMUL_REPS` | 2 | Кількість повторів множення (береться найкращий) |
| `LAB3_FS_ITERS` | 4000000 | Ітерацій на потік у тесті false sharing |
| `LAB3_RACE_ITERS` | 1000000 | Ітерацій на потік у тесті перегонів |
| `LAB3_ROWS_N` | 2048 | Розмір матриці в тесті обходу |

Приклад:

```bat
set LAB3_THREADS=4
set LAB3_MATMUL_N=512
cache_bench.exe results\small.csv
```

## Формат CSV

Файл пишеться з UTF-8 BOM, щоб Excel на Windows коректно відкривав кирилицю.
Перший стовпець — тип рядка:

- `INFO` — параметри прогону (потоки, розміри, розмір кеш-лінії з ОС);
- `LATSEQ,<КБ>,<байтів>,<ГБ/с послідовно>,<нс послідовно>,<нс випадково>,<Моп/с випадково>` — затримка і пропускна здатність;
- `STRIDE,<крок>,<елементів>,<нс>,<ГБ/с корисних>,<ГБ/с трафіку ліній>`;
- `CACHELINE,estimate,<байти>,min_ns,<нс>` — оцінка лінії за стрибком ціни;
- `MATMUL,<варіант>,<n>,<с>,<ГФлоп/с>,<контрольна сума>`;
- `FALSESHARE,<режим>,<потоків>,<операцій>,<с>,<Моп/с>,<очікувано>,<фактично>,<статус>`;
- `CONTENTION,<режим>,<потоків>,<операцій>,<с>,<Моп/с>,<фактично>,<очікувано>,<втрачено>,<статус>`;
- `ROWS,<режим>,<n>,<с>,<ГБ/с>,<сума>` плюс рядок `ROWS,equal,<n>,OK|FAIL`.

Статус `OK` означає, що лічильник збігся з очікуваним, `LOST` — що оновлення
загубилися (очікувана поведінка для `volatile`).

## Самотестування

`cache_bench.exe --selftest` перевіряє:

- що перестановка для тесту затримки є одним циклом і відвідує кожен елемент рівно раз;
- що всі чотири варіанти множення дають однаковий результат на `n = 129`
  (розмір спеціально не кратний блоку 64);
- що суми по рядках і стовпцях збігаються;
- що лічильники false sharing і коректні режими перегонів точні, а `volatile`
  не перевищує очікуване значення.

Тест на некратному розмірі свого часу зловив помилку в блочному множенні, тому
`n = 129` — не випадкове число.

## Результати

Усереднено за трьома прогонами на AMD Ryzen 7 5700 (8 ядер / 16 потоків,
32 КБ L1D і 512 КБ L2 на ядро, 16 МБ L3), Windows 11, MinGW-w64 GCC 16.1.0.

| Ефект | Результат |
|---|---|
| L1 (16 КБ) проти DRAM (128 МБ) | 1,09 нс проти 97 нс — **89×** |
| Послідовно проти випадково на 128 МБ | 0,27 нс проти 97 нс на елемент — **354×** |
| Крок 64 Б проти 8 Б | 2,04 нс проти 0,47 нс — **4,3×** |
| `ikj` проти `ijk` | 19,12 проти 0,39 ГФлоп/с — **49×** |
| False sharing: padded проти unpadded | 10 976 проти 169 Моп/с — **65×** |
| `volatile` | 1 192 737 із 8 000 000 — втрачено **85,1 %** |
| `atomic_padded` проти спільного `atomic` | 4 258 проти 101 Моп/с — **42×** |
| Рядки проти стовпців | 34,3 проти 1,90 ГБ/с — **18×** |

Сирі дані трьох прогонів — у `results/run1.csv` … `results/run3.csv`.

## Обмеження

Вимірювання виконані на одній машині, без закріплення потоків за ядрами й без
апаратних лічильників `perf`, тому промахи L1/L2/L3/DRAM не розділяються
напряму. Абсолютні цифри залежать від частоти й планувальника; стійкими є
порядки величин і кратності. Оцінка розміру кеш-лінії за кроком наближена —
точне значення береться з ОС через `GetLogicalProcessorInformationEx`.

## Структура репозиторію

```

build.bat            збірка на Windows / MinGW-w64
cache_bench.exe      зібраний бінарник (Windows x64)
results/             сирі результати трьох прогонів
Звіт_ЛР.docx         звіт із методикою, таблицями та висновками
```
